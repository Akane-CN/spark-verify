## 2. 交付内容

| 内容 | 说明 |
| --- | --- |
| 运行器 `ckb-verify run` | 在全新的 OffCKB devnet 上执行 `verify.toml`，由运行器提交交易，逐条检查声明，写出 `report.json` |
| 两份冻结的 manifest 规范 | `0.1.0`：cycles、按脚本筛选的 Cell、数据和容量、CKB 与 UDT 余额。`0.2.0`：部署仓库自己的脚本、命名引用、pure step、`expect.error.group`、节点拒绝 |
| 失败归因 | 没有结论的运行会标出停止阶段（`ERROR [stage]`），区分项目自己的命令、工具链和 manifest 的问题 |
| 离线复核 | `validate`、`digest`、`check-digest`、`check-bundle`：不联网、不执行任何命令，重新推导声明、结论和摘要 |
| 本地控制台 `ckb-verify ui` | 校验、运行、看报告（交易画成输入和输出 Cell）、比较两次运行、离线校验他人的报告 |
| 项目接入脚本 `setup-project` | 一条命令把安装包接入用户项目，可生成能直接跑通的示例 |
| 可复用 CI 工作流 | 用户仓库一行 `uses:` 即可在每次提交时运行，并保存报告 |
| 五个 showcase | secp 转账、Cell 属性、CKB-UGMP Spore、词汇表（xUDT）、仓库脚本部署 |
| 发布与维护材料 | 发布清单、runbook、发布说明草稿、独立审查指南、维护循环、版本策略 |

## 3. 收尾阶段做的加固

这一轮的目标是把"能跑"变成"别人能稳定地用"：

1. **下载自动重试。** 固定版本的 CKB 和 debugger 安装包在遇到网络错误或 HTTP 408、429、5xx 时最多尝试四次。起因是 2026-11-09 GitHub 下载返回 504，导致 CI 失败。重试不放松校验：每次下载的内容都要通过同样的长度和哈希检查；超时、其他状态码和校验失败不重试。
2. **CI 缓存。** 本仓库的 showcase job 和给用户用的可复用工作流都会缓存校验过的安装包。缓存不被直接信任，运行器会重新按哈希校验。
3. **一条命令接入。** 以前接入一个项目要手动做七步，其中补丁文件必须在第一次 `bun install` 之前放好，容易出错。现在由 `src/setup-project.ts` 完成，它也可以直接从安装包里取出来运行，不需要检出本仓库。安装验收矩阵改为通过它安装，并实际运行它生成的示例，所以文档里的步骤就是门禁覆盖的步骤。
4. **`elliptic` 豁免续期。** 原豁免 2026-11-25 到期，到期后本仓库的供应链门禁会失败。已应用 2026-11-03 准备好的续期补丁，新的到期日是 2026-12-25；依据见 [续期记录](../waiver-renewal-fallback.md)。这是一个安全策略决定。如果你不同意，执行 `git apply -R docs/fallback/elliptic-waiver-renewal.patch` 就能撤销。
5. **README 使用说明**，以及对应的中文版。

## 5. 已知限制

- 只支持 Linux x64、Bun 1.2.19、Node.js 22。只有 CKB `0.209.0` 有固定的安装包。
- 没有沙箱：`verify.toml` 会执行仓库自己的命令，只能用于可信的仓库。
- 每个步骤一笔交易。不支持测试网和主网。
- 报告的离线有效性是内部一致性，不是真实性证明，没有签名。
- PASS 的含义是"声明的检查在记录的环境里全部通过"。它不是安全审计，也不能证明 manifest 写全了。
- 完整列表见 [发布说明草稿](../release-notes-draft.md#known-limitations)。
