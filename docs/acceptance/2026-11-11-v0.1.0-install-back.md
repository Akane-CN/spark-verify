## Re-run after the fixture fix

**What was wrong.** The runner publishes the cached `ckb-debugger` read-only (mode `0500`). The `tampered-debugger-cache` fixture overwrote it with `dd` without allowing the write. Root ignores the mode, so the first run above corrupted the cache and the row passed for the right reason. An ordinary user's write is refused. The fixture did not check that, ran the runner against the clean cache, got exit 0, and reported it as a failed tamper check. The runner's integrity check was not bypassed in either run.

**The fix** (`scripts/acceptance-matrix.sh`, commit `3cb24c8`): allow the owner write, invert one byte at a fixed offset, restore the mode, and require that the hash changed. Otherwise the row fails as a fixture setup failure and the runner is not invoked. A pass now also requires the corrupted bytes to be still in place after the runner refused them. The results header records the uid.

**Checked in isolation**, with the fixture block run against a stand-in cache:

| Case | Row result |
| --- | --- |
| The write is refused | FAIL: "fixture setup failed: chmod u+w was refused; runner not invoked" |
| The cache is corrupted and the runner refuses it | PASS |
| The cache is corrupted and the runner wrongly returns exit 0 | FAIL |
